# ユーザー作品の作成・公開・プレイ：実装方針

- 作成日: 2026-10-04
- 状態: 実装予定。今回の変更は設計文書とIssueのみ。
- 調査基点: `98eced1293af393952ef1a0f390d90e07e9da3a0`
- 仕様の正本: [詳細設計書](story-authoring-design.md)
- 本書は作業分割・移行・検証・完了判定の正本。仕様を別計画に複製しない。

## 1. 目的と優先順位

ユーザーが確認した最優先事項は任意作品の実行基盤である。投稿UIやAI生成を先行させず、既存2作品と異なる第3作品を本体コード変更なしで動かす。

次に版固定と編集・試遊・限定公開を通し、AI作成補助、一般公開へ広げる。AIによる整合性調整は作者の原稿への提案とし、作者の意図や編集中の変更を黙って上書きしない。拡張性は保存・実行・編集・テンプレート・生成の境界で確保し、無制限のルールエンジンを初期に作らない。

## 2. 段階と出荷条件

| 段階 | 対象 | 出荷条件 |
| --- | --- | --- |
| M0 任意作品実行 | S1〜S3 | 異なる第3作品をDB登録し、開始・結末・再開。旧runも互換 |
| M1 手動作成と限定公開 | S4〜S7 | Aがフォーム作成・試遊・公開しBが完走。第2版公開でも第1版run不変 |
| M2 AI作成補助 | S8〜S9 | フォーム補完と自然文生成が作者の確認・共通検証経路に載る |
| M3 一般公開 | S10 | 一覧、参加、quota、通報・停止、公開環境受入 |

M2とM3はM1後に独立して進められる。一般公開する機能には対応する費用・同時実行制限が必須。P0/P1/P2は本機能内の優先度であり、既存障害・セキュリティ修正を後回しにする意味ではない。

## 3. 作業分割

### S1: [P0] 任意作品を実行できるScenario定義・初期化・整合性検証へ一般化する

依存: なし

意図: 投稿UIより先に、ゴブリンや既存作品名に依存せず別作品を実行できる土台を作る。自由行動とEngineによる確定を維持する。

実装範囲:

- NPC/敵、配置、能力、初期所持品、許可済みアイテム効果・判定を型付きデータ化する
- 作品固有の矛盾チェックを旧版互換へ隔離し、新規作品は構造化された保護事実を検証する
- 公開/秘密/作者専用の情報区分と対応capabilityを定義する
- schema追加だけでなく初期化・攻撃・技能・アイテム・表示まで参照解決する

完了条件:

- [ ] 本体のscenario_ref分岐を追加せず、既存とは異なるNPC・敵・アイテムの第3作品を開始・完走できる
- [ ] 非戦闘作品に固定ゴブリンが生成されない
- [ ] 旧v1/v2/v3の進行、自由行動、早期達成・撤退を回帰確認する
- [ ] 未知の機能・範囲外能力・解決不能参照を実行前に拒否する

### S2: [P0] 作品・下書き・不変版・プレイ参照のDB保存と旧作品移行を実装する

依存: S1

意図: 作者の編集やテンプレート更新で、プレイ中のストーリーが突然変わらないようにする。下書きrevisionと公開版・schema/ruleset版を区別する。

実装範囲:

- stories/drafts/draft_revisions/versionsおよび検証・試遊参照のmigrationを設計する
- 公開版・試遊版のpayload不変性、同一作品FK、一意制約、参照中削除制限を実装する
- runにstory_version_idを追加し、旧ref/versionから再実行可能なimport/backfillを行う
- ADR-0012の適用範囲を更新する後継ADRと移行手順を記録する

完了条件:

- [ ] 既存保存runの状態・IDを再生成せずに旧版を再開できる
- [ ] 同じimportを再実行しても版・対応が重複しない
- [ ] 参照中の版を通常アプリ権限で書換え・削除できない
- [ ] 未完成payloadを原稿として保存でき、公開データとは分離される

### S3: [P0] API・worker・冒険一覧を不変Scenario版の共通取得経路へ切り替える

依存: S2

意図: 開始時だけDB化しても、再開やworkerが組み込み・最新版を読むと版固定が崩れるため、全経路を統一する。

実装範囲:

- ScenarioRepository/Resolverを導入してBUILTIN_SCENARIOS依存を監査する
- AdventureService、保存済み一覧、TurnQuery、解決/描写workerに版を供給する
- 初期化・run保存をatomic化し、開始要求の冪等性を維持する
- 互換readerとimmutable版ID/hashのキャッシュを用意する

完了条件:

- [ ] DBへ登録した第3作品が開始・結末・再開まで動く
- [ ] 公開版更新後も既存runの設定と表示タイトルが変わらない
- [ ] 同一開始要求の応答喪失再送でCampaignが増えない
- [ ] APIとworkerが同一版を読み、未知schemaを最新版として解釈しない

### S4: [P1] 下書き編集API・自動保存・履歴復元・所有者認可を実装する

依存: S2

意図: 未完成でも作業を失わず保存し、複数タブやAI生成結果で新しい編集が上書きされないようにする。

実装範囲:

- 原稿用の緩い型と実行定義用の厳しい型を分離する
- expected_revision/request_idによる比較更新と再送処理を実装する
- 保存状態表示、debounce、失敗時入力保持・再試行、未保存離脱警告を実装する
- 履歴復元は新revision、自作品複製は新story IDにする

完了条件:

- [ ] 未入力・参照切れ・結末なしでも下書き保存できる
- [ ] 競合は409となり片方の入力が黙って失われない
- [ ] 保存応答喪失後の同一要求再送が同じrevisionを返す
- [ ] 他作者の原稿・履歴の閲覧更新を拒否する
- [ ] 公開・試遊は最新保存完了後のrevisionを対象にする

### S5: [P1] 拡張可能なテンプレートregistryとフォーム式作品エディタを実装する

依存: S1, S4

意図: 非技術者がテンプレートから作成でき、将来テンプレートを増やしても既存作品や画面に作品別の分岐を増やさない。

実装範囲:

- template ID/version・初期原稿・質問・フォーム部品・必要capabilityを定義する
- 基本情報、世界、場所、人物、アイテム、条件、結末、AI裁量のフォームを実装する
- 内部refを安定IDへ変換し、作者には意味のあるラベルを表示する
- fixed/fillable/undecided、公開情報/秘密の入力区分を設ける

完了条件:

- [ ] 少なくとも異なる2テンプレートから原稿を作成できる
- [ ] 追加テンプレートをregistry経由で表示し、既存作品が自動変更されない
- [ ] 未対応capabilityを明示し、任意HTML/JSを実行しない
- [ ] 自動保存と履歴をフォーム全体で利用できる

### S6: [P1] 共通コンパイル・公開前検証・版固定の作者試遊を実装する

依存: S3, S4, S5

意図: 文章として成立することとゲームとして実行できることを分け、同じ検証経路を手動・AI作成の双方で利用する。

実装範囲:

- field_path/code/severity/coverage付き検証レポートを返す
- 参照・初期化・ルール・能力・数値上限とフラグ込み到達可能性を検証する
- 探索予算超過は未検証警告とし、全自由入力経路の成功を保証しない
- playtest snapshot、作者限定debug、結末到達記録を実装する

完了条件:

- [ ] 単純グラフでは通るがフラグ条件で詰む例を検出する
- [ ] 原稿編集後も既存試遊の内容が変わらない
- [ ] 検証結果と試遊記録が対象hashに結び付き、古い結果を公開に流用できない
- [ ] 作者以外にdebug情報・秘密情報を返さない
- [ ] 状態強制変更した試遊を公開条件の完走に数えない

### S7: [P1] 不変版の公開・限定共有・作品詳細・別ユーザーのプレイを実装する

依存: S6

意図: 作者がコードを書かず作成し、別アカウントが最後まで遊べる最小の循環を完成させる。

実装範囲:

- 公開transaction、公開候補revision照合、request_id冪等性を実装する
- private/unlisted/publicとwithdrawn/blocked/archivedの意味を分離する
- マイ作品・公開詳細・プレイ開始・通常公開停止・自作品複製を接続する
- 公開DTOと作者DTO、player stateを分離する

完了条件:

- [ ] Aが公開した第1版をBがプレイし、Aが第2版公開後もBは第1版を再開できる
- [ ] 新規開始は現在版を使い、画面表示後の版変更を黙って適用しない
- [ ] 公開停止で新規開始だけを止め、既存runを保持する
- [ ] unlistedは一覧非掲載だがURLを知る認証ユーザーは開始可能、privateは作者限定
- [ ] 同時公開・公開と編集/停止の競合を検証する

### S8: [P2] フォーム原稿のAI整合性確認・補完と非同期提案採用を実装する

依存: S4, S6

意図: 入力から整合した物語・分岐を補完するが、作者の固定設定や生成中の新しい編集をAIが黙って書換えない。

実装範囲:

- 整合性確認/不足補完を明示ボタンで実行し、自動保存では呼ばない
- base_revision固定のauthoring job、lease/timeout/再試行上限/使用量を実装する
- 安定ID単位の差分・変更理由を返し、作者が採否を選ぶ
- fixed/fillable/undecidedと原稿のデータ扱い、ゲームworkerと別の処理枠を実装する

完了条件:

- [ ] revision 10生成中に11保存した場合、10の結果が11を自動上書きしない
- [ ] 固定設定の矛盾は警告し、AIの固定解除指示は適用しない
- [ ] 同一ジョブ再配信・提案採用再送で原稿や結果を二重確定しない
- [ ] 失敗・キャンセル・上限超過が見え、原稿が失われない
- [ ] 秘密を含む入力/結果を他ユーザーに返さない

### S9: [P2] 自然文の条件から構成案・実行定義候補を生成する

依存: S5, S8

意図: ユーザーが舞台・難易度・目的・雰囲気を指定して作品を作れるようにする。直接公開せず作者の確認と共通検証を通す。

実装範囲:

- 構成案→作者修正/承認→具体化→検証→提案採用の導線を実装する
- 生成で既存template/ルール/capabilityを使い、未対応機構を捏造しない
- 不足や矛盾の再提案は回数・token予算内で行う

完了条件:

- [ ] 自然文から原稿を生成し、作者が編集して試遊・公開できる
- [ ] 未検証生成JSONが公開/実行されない
- [ ] 固定項目とundecidedが保持され、既存編集との競合がS8と同じ処理になる
- [ ] 失敗した生成でも再試行前の原稿を失わない

### S10: [P1: 一般公開前] 作品発見・参加登録・利用制限・通報と運営停止を実装する

依存: S7

意図: 限定公開の成功後、不特定ユーザーの利用に必要な発見・認可・費用管理・運営を整える。収益化は後回しでも無制限利用にはしない。

実装範囲:

- public作品の新着一覧・検索・タグ・cursor paginationを実装する
- 既存OIDC事前登録に加え一般参加フローと最低限の表示プロフィールを用意する
- 用途別quota・同時実行/サイズ制限・全体予算停止・集計を実装する
- 通報、管理者停止/解除、監査と継続中workerへの停止反映を実装する

完了条件:

- [ ] unlisted/private/withdrawn/blockedが公開一覧へ漏れない
- [ ] 他人の会話ログを作者へ提供せず集計だけを返す
- [ ] 運営blocked後はAPI・workerの確定境界で継続を止める
- [ ] quota/並行要求で上限をすり抜けず、再送を不当に二重計上しない
- [ ] 既存#19のHTTPS/OIDC/SSE受入を確認し、人の評価#24〜#28と技術検証を区別する


## 4. 変更境界

- Domain/Contracts: 作者原稿と実行定義を別の型にし、公開レスポンスを第三のprojectionにする。
- Application: Compile/Validate/Publish/Playtest/ApplyProposalなどのユースケースを追加。HTTP handlerへ処理を集中させない。
- Infrastructure: PostgreSQL保存、版取得、migration、authoring job workerを実装。DB取得後の純粋な進行判定を維持。
- Frontend: App.vueのプレイ画面から作者画面を分離し、契約型と保存状態管理を共通化する。
- LLM: 既存Pydantic AIの境界を活用し、入力snapshot、構造化出力、予算を明示。AI生成は手動と同じコンパイラを通す。
- Template: 同梱registryと許可されたフォーム部品から始め、テンプレート更新を公開版変更に結び付けない。

## 5. 保存移行と切替手順

1. 新テーブルとnullableなrun版参照を追加する。既存JSONと旧readerは保持する。
2. 既存の全scenario_ref/versionを調査し、同じ内容を一意のimmutable版へimportする。v1/v2も省略しない。
3. 旧runへ対応する版IDをbackfillする。Campaign/Scene/Entity/Turn/Eventを再生成しない。
4. import件数、未解決参照、content hash、旧run再開の検証を記録する。
5. APIと全workerを共通Resolverへ切り替える。移行期間のmixed deploymentで未対応版を読むworkerが稼働しない配置手順を作る。
6. 新規のユーザー作品開始を有効化する。旧組み込みfallback撤去は依存検索と未移行件数ゼロを確認してから行う。
7. 新データを旧binaryで読めないため、障害時は新規作成を停止し互換readerのある版へ切り戻す。データ削除を伴う安易なdowngradeではなくforward-fixを基本にする。

PRはschema一般化、DB追加/import、読取切替などレビュー可能な単位に分ける。途中段階の未完成authoring APIを一般公開しない。後継ADRでADR-0012のDB保存判断の変更と、ADR-0016の維持する境界を記録する。

## 6. 検証戦略

| 領域 | 意味のある検証 |
| --- | --- |
| 任意作品 | 非戦闘作品、既存と異なる敵/アイテム、未知capability拒否、第3作品の完走 |
| 互換性 | 礼拝堂v1/v2/v3・灯台の保存済みrun再開、自由行動・重大リスク確認の回帰 |
| DB制約 | immutable更新拒否、FK、一意性、import再実行、公開と編集/停止の競合 |
| 自動保存 | 複数タブ、応答喪失再送、保存失敗保持、履歴復元の新revision |
| 版固定 | v1プレイ中にv2公開、通常停止後の再開、試遊中に原稿変更 |
| AI | 10→11編集競合、固定項目改変案、再配信、timeout、予算上限、秘密の権限 |
| 公開情報 | 作者/プレイヤー/未ログインのDTO、秘密・未発見結末の非露出 |
| UI | 作成→自動保存→検証修正→試遊→公開→別アカウントで開始 |
| 運営 | blockedと実行確定の競合、quota並行消費、検索への非公開混入防止 |

有限状態検証の成功と自由入力全体の保証を混同しない。Fake・エージェント・実モデルの技術確認と人の楽しさ評価も分ける。必要な回帰テストは実装時に追加し、文書変更だけの今回にはゲームテストの実施を主張しない。

現在の開発用コマンドはREADME/developmentに従う。初期候補は `uv run --frozen pytest tests/unit tests/contract -q -p no:cacheprovider`、`uv run --frozen ruff check .`、`uv run --frozen mypy src`。DB変更時は専用PostgreSQL環境でmigrationと該当統合テストを実行し、最終統合時に必要な全DB suiteを最終コードで確認する。DB未設定skipを成功としない。UI変更時はfrontendのtest/typecheck/buildと同一originでの確認を行い、リポジトリ方針に従い生成物も更新する。

## 7. 既存Issueとの関係

- #16: 自由行動と登録済み帰還の報酬条件統一。一般化で同じ不整合を持ち込まない。着手時に最新状況を確認する。
- #19: 公開HTTPS/OIDC/SSEの受入。M3の環境ゲートとして参照し、重複起票しない。
- #24〜#28: 人の初回操作・意図一致・代償・楽しさ・プレイ時間の評価。技術的な完走で代替しない。新作者UIの評価観点を必要に応じ追加する。

既存Issueは今回の設計追加だけでcloseしない。現行open一覧を確認した範囲では本書のauthoring基盤と同等の実装Issueはなく、専用の親IssueとS1〜S10を起票する。

## 8. 将来の実装作業での計画管理

.AGENTS.mdは大規模実装時に日本語ExecPlanを.agent/へ作成・更新するよう求めている。今回の文書作成では必須ではない。基点treeにはPLANS.mdは確認できなかったため、実装着手時に所在・最新ルールを再確認し、既存ExecPlanの様式を参考にする。

実装時のExecPlanは本書・詳細設計書とIssueを参照し、実行状況、調査結果、検証証拠、変更した判断だけを記録する。同じ仕様を別形式で複製しない。

## 9. 未決定事項の解決方法

具体的なquota、token、地点数/文字数の上限、保存履歴保持、provider/modelは設定値として分離し、実測と予算により決定する。未定値を無制限として実装しない。基本方針の再承認を待つ必要はない。

公開条件は同一compiled hashで作者が少なくとも1結末に到達し、ブロッキングエラーがなく警告を確認したこと。これは会話の「作者試遊・公開前検証」を実行可能な初期基準へ具体化したもの。完全な経路検証や面白さの保証ではない。将来緩和・強化する場合は理由と受入変更を記録する。
