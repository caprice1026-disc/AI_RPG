# ADR-0017: 利用者が作る作品と不変の実行版

- 状態: 採用
- 決定日: 2026-10-04
- 置換対象: [ADR-0012](0012-scenario-definitions-and-progress.md)の「定義をリポジトリだけに置き、PostgreSQLには実行状態だけを保存する」という制約
- 維持する判断: [ADR-0016](0016-bounded-open-scenario.md)の自由行動を検証して確定するゲーム処理、および既存runの互換性

## 背景

組込みJSONだけを実行対象とする構成では、利用者がブラウザで原稿を書き、試遊して他の利用者へ公開できない。編集中の原稿は参照切れや未入力を含む一方、進行中の冒険は開始時に検証した定義を使い続ける必要がある。

そこで、編集可能な下書き、検証済みの不変な実行版、Campaignごとの実行状態を分離する。AIの提案を作者が確認して原稿へ反映する操作と、プレイ中にEngineがゲーム状態を確定する操作も分離する。

## 下書き・版・実行状態

作品の所有者、公開範囲、公開状態と、下書き・履歴をPostgreSQLで管理する。下書きは `AuthoringDraft` としてサイズを制限し、未完成でも保存できる。保存は `expected_revision` による楽観的競合検出と `request_id` による冪等性を使う。履歴の復元は新しいrevisionを作り、過去の原稿を上書きしない。

試遊または公開するときは、下書きから型付きの `ScenarioDefinition` を検証し、`story_versions` に不変のpayload、content hash、schema・ruleset・必要機能を保存する。公開版にはrelease番号を付ける。Campaignは `story_version_id` に固定し、snapshotへその定義を読み込む。DBに結び付いたrunの定義が欠けたときは処理を拒否し、最新catalogで置き換えない。

組込みJSONは配布物として残し、API起動時に過去の対象versionもDBへ冪等に取り込む。旧runの未設定の参照は同じscenario ref・versionへ結び付け、HP・在庫・進行を再初期化しない。作品の編集、新しい公開版、公開停止は、開始済み冒険の定義を差し替えない。

## 初期状態と既知の機能

新しい作者作品はschema 2の明示的な初期状態を持つ。NPC・monster・itemのref、能力値、所有、装備、Sceneへの配置、公開範囲を検証し、既存のゲーム用テーブルへ初期状態を作る。非戦闘作品に固定の敵は追加しない。実行できる作品を特定の `scenario_ref` に限定しない。

能力と効果は実装済みのallowlistで制限する。現時点の技能難易度は `easy`・`normal`・`hard`、初期武器ダイスは `1d4`・`1d6`、アイテム使用効果は `healing_potion` のみとする。アイテムrefや表示名と効果を分け、効果は固定した定義から解決する。公開inventoryにはnullableな `effect_ref` を付ける。任意のスクリプト、自由なダイス式、新しいゲームルールを作者が注入する機能は追加しない。

保護する事実にはentity・場所・取得flagの参照と公開範囲を持たせる。登録行動と自由行動で取得場所や参照の衝突を検査し、公開contextから未公開・作者専用の事実を除く。旧短編固有の文字列検査はlegacy policyに隔離する。この構造検査で自然言語の全ての矛盾を判別できるとはしない。

## 検証・作者試遊・公開

構造検証はLLMを呼ばない。型、参照、初期状態、対応機能を検証し、登録行動と有限のflag状態から到達経路を調べる。上限到達は部分検証として扱う。戦闘は抽象化した結果で探索するため、自由入力、文章の意味、秘密の表現、生存可能性やゲームバランスは保証しない。報告にはエラー、警告、検証範囲を分けて保存する。

公開には、最新の下書きrevision・hash・validator versionと一致するエラーなしの検証結果、全警告の確認、同じ定義hashの作者試遊が少なくとも1つの結末に到達した記録を必要とする。debugで改変した試遊は使わない。作者本人の `author_playtest_acknowledged` も必要であり、自動テストやエージェントの完走を人の確認の代わりにしない。

公開範囲は `private`、`unlisted`、`public` とし、公開状態は有効・公開停止・運営による停止・アーカイブを分ける。検索一覧は一般公開の有効な公開版を対象とし、公開・限定共有の紹介では公開メタデータだけを返す。下書き、作者メモ、秘密の定義は公開DTOへ含めない。冒険開始時に認証、版の利用権限、作品の状態を再確認する。

## 作者が明示的に依頼するAIジョブ

自動保存でLLMを呼ばず、作者の操作で `check`、`fill`、`outline`、`concretize` のジョブを作る。構成案は作者が編集・承認し、その承認revisionから具体化する。構成案の変更後は承認し直す。

authoring-workerはゲームの解決・描写workerと別processで動き、受付時の下書きsnapshotとモデル設定を使う。AIの出力は変更前後・理由を持つ提案として保存する。固定項目と安定したrefを守り、作者が選んだchange IDだけを採用して新しい下書きを作る。元のrevisionが変わっていれば409で拒否し、自動でマージ・公開しない。

ジョブの状態、lease、要求回数、利用量をDBへ保存する。1ジョブの物理LLM要求は最大1回とし、SDKの自動再送・修復を無効にする。受付数、同時実行数、入力サイズ、token予算、timeoutを制限する。キャンセルは既に送信したprovider要求の返金や、確定した利用量の取り消しを保証しない。

## 認証・利用制限とゲーム処理の維持

参加登録は既定で無効とし、有効な場合だけ `/auth/login?join=true` の明示的なOIDCフローで受け付ける。通常ログインとBearer APIから自動登録しない。作品や原稿の所有者認可、ゲームのCampaign membership・Actor認可、ブラウザのOrigin・CSRF確認はそれぞれ継続する。

日次・同時実行の利用上限と受付停止をDBで管理し、同じ要求の再送で利用量を増やさない。管理者による作品停止や通報の処理はゲーム状態の編集権限とは分ける。設定値は[開発ガイド](../development.md#authoring-limits)と[設定例](../../.env.example)を参照する。

ADR-0016のゲーム処理は置換しない。LLMは行動を提案し、Applicationが参照、所有、現在地、許可された効果を検証してからEngineへ渡す。Engineが乱数・数値を決め、Action・Event・Canonical State・進行・Turnを同じtransactionで確定する。重大リスクの確認、Campaign lock、state version、lease、冪等性、描写再試行でゲーム処理を繰り返さない規則も維持する。

## 採用しない案と残る確認

- 編集途中の下書きを進行中runから直接読む案は、再開時に条件や効果が変わるため採用しない。
- AIの生成結果を自動保存・自動公開する案は、固定項目や作者の採否を飛ばすため採用しない。
- 検証に通れば作品が常に成立すると扱う案は、自由入力と文章の意味を網羅できないため採用しない。

人による作者操作・試遊・公開の受入確認と、公開HTTPS環境の[Issue #19](https://github.com/caprice1026-disc/AI_RPG/issues/19)の受入条件は未解決である。ローカルComposeは固定の開発プレイヤーを使うHTTP構成であり、公開運用の受入確認にはならない。実行したテストやブラウザ確認の結果は別の検証記録へ残す。
